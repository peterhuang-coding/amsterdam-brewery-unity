# Amsterdam Brewery 核心功能与证据口径

## 核心功能

如果只能保留一个核心，它是：

> 玩家围绕未来订单，在有限时间里决定酿什么、怎么处理、卖给谁，并让这些选择改变之后几天的局面。

它由三个不可拆开的部分构成：

| 机制 | 玩家实际在做什么 |
| --- | --- |
| 生产与销售闭环 | 同一批酒的数量、品质、风味和成熟时间决定能满足谁 |
| 有期限的日程与订单 | 在即时现金、未来承诺和课程时间之间取舍 |
| 有代价的分叉 | 快熟与慢熟、减量保质与风味转向都改变后续用途 |

批次数据只是骨架，玩家价值是“今天的选择改变明天怎么玩”。节庆用于改变每局条件；偷窃和逃票是后续供给路线；冲浪保持独立，不必为经营产出资源。

## 证据分层

### 已有外部案例支持

《潜水员戴夫》的公开机制把白天采集、晚上经营和装备升级连接起来；独立评测也描述了新菜谱如何反过来为第二天采集提供目标。这支持“两个玩法互相提供目标”的结构，但不能证明照搬到本项目一定成功。

- [DAVE THE DIVER 官方商店说明](https://store.steampowered.com/app/1868140/)
- [PC Gamer：DAVE THE DIVER 评测](https://www.pcgamer.com/dave-the-diver-review/)（2023 年评测，可能已过时，仅作设计结构参照）

### 有小样本玩家反馈提示风险

本轮定向查看了《Travellers Rest》近期英文正负评各五条。负面样本有人认为强制小游戏与采集挤占酒馆经营；正面样本有人喜欢原料组合、制作和持续任务。这些样本只能提示“支线是否挤占核心体验”值得测试，不能推断整个市场，也不能得出小游戏一定越少或越多越好。

- [负面样本：支线挤占酒馆经营](https://steamcommunity.com/profiles/76561198136214917/recommended/1139980/)
- [正面样本：制作组合与任务循环](https://steamcommunity.com/profiles/76561198334404409/recommended/1139980/)

### 本项目代码能证明的是结构缺口

调研快照中，酿酒会直接增加现金和分类库存，但批次品质与来历没有持续进入销售；酒吧缺货时仍可以替代酒完成交易。因此优先强化生产与销售之间的联系，是基于实现事实的设计判断。

- [销售结算代码快照](https://github.com/peterhuang-coding/amsterdam-brewery-unity/blob/12995e2d6c47691795cde18864f9a13fa21cf887/tools/prototype/index.html#L5257)

## 尚未被证明的部分

以下仍是待验证假设，而不是数据结论：

- “阿姆斯特丹学生＋季节主题周＋酿酒肉鸽”是否能吸引目标玩家；
- 批次抢救是否比直接成功/失败更有趣；
- 有代价的规则卡是否提高复玩；
- 三日闭环是否能转化成稳定的七日游戏；
- 这些机制是否能提高留存或付费。

因此当前应称为“优先验证的核心功能”，不能写成“已经被外部数据证明的高价值功能”。

## 下一步验证

用五至八位目标玩家做形成性试玩，重点观察：

1. 是否因为第三天订单主动改变今天的酿造或销售；
2. 出现批次偏差后是否继续，并能解释两个补救选项的差异；
3. 能否说明一批酒为什么可以或不可以交付；
4. 结束后是否主动想开第二局，并说出下一局想改的策略。

小样本用于发现问题，不用于证明留存提升。只有本项目自己的玩家行为，才能决定这套核心是否继续投入。
