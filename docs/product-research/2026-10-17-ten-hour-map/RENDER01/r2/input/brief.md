# RENDER01: actual geography in the brewery game

Build a standalone Canvas2D map renderer. The user finds the current map too simple, with too little street detail and too little resemblance to Amsterdam. The parent downloaded official BGT water, building, road and bridge-part polygons over approximately7.1 by6.7 kilometres (145703 features). The supplied fixture is an exact local subset. Follow geo-interface.md. Adoption into the game is a later parent decision; edit no existing game code.

## Visual direction
Preserve canal #378e9b, ink #183b48, brick #b86b4c, sand #e2d4b0, lamp #ffd184 and slate #253d49. Use muted stone ground, cool water, light roads and subdued brick/slate footprints by day; navy ground, cool water and warm markers by night. Actual canal shapes and dense irregular footprints carry the identity. Consider technical GIS, fabricated3D scenery and a restrained miniature-city top-down treatment; implement the last, with subtle cosmetic shadows and roof tones. Do not invent heights, facades, parks, canals or a rectangular street grid. Shadows never change footprints. Avoid excessive labels or decorative cards. Distinguish roads, water, buildings and bridge decks; piers must not look like usable decks. Read reopening-scene-reference.js for visual continuity without editing it.

## Frozen module API
Expose UMD globalThis.AmsterdamGeoRenderer and module.exports. No imports, automatic fetch or network calls in the module. Export create(data, {canvasFactory} = {}); pure helpers may support tests.
Instance draw(ctx,view,options={}) returns {transform:{scale,tx,ty},markers:[{id,x,y,radius}],labels:[{id,text,x,y,width,height,fontCssPx}],visibleBounds:[minx,miny,maxx,maxy]}. Also provide stats() with measured counters and dispose() releasing caches.
The caller already scales its context for DPR. Drawing coordinates are logical pixels. Options default to width1100,height640,cssWidth=width. places is an array of {id,name,district,icon,x,y}; optional gardenEntry has the same shape. Marker positions are logical canvas coordinates for caller hit-testing. The transform maps world metres to logical pixels with an exact inverse.
View follows the current game: {position:{x,y,visited:[],bike:{x,y,mounted,pushing}},path:[{x,y,transport?}],target,zoom:1|2,camera:'street'|'city',mode:'map'|'place',place,afterHours,flowerCart:{x,y},garden,reducedMotion,time}. Handle missing optional fields sensibly; reject invalid required data or nonfinite player positions. No dependencies on window.City or FlowerNetwork. Do not mutate inputs. Balance save/restore and preserve caller transform/styles; never reset its DPR transform.
City overview fits the world at zoom1, follows/clamps at zoom2. Street view follows the player at about2 CSS pixels per metre, deriving logical scale from cssWidth. Do not derive street scale from a whole-city fit: real houses and narrow roads must remain visible at CSS width390. Clamp or letterbox at world edges. Test CSS widths320,390,1100.

## Geometry and performance
Render every ring of selected polygons, including holes with even-odd fill and gaps between multipolygon components. Bounds can extend beyond the requested bbox; clip drawing to the world extent. Keep geometry immutable.
Build a spatial index once and cull by visible bounds. Use bounded offscreen static caches for city overview and padded street views so unchanged frames do not scan/redraw all145703 features. canvasFactory(width,height) supports browser/tests; otherwise use OffscreenCanvas or document.createElement('canvas') if available. A few canvases, each no larger than2048 by2048, suffice. Avoid an unnecessary tile framework or unbounded eager Path2D allocation. Without cache capability, direct drawing may be a truthful fallback; the browser cache path must work. Invalidate for day/night, size, scale and camera leaving the cached area. stats expose builds/reuses and indexed/culled/drawn counts. Parent measures actual packed full-source performance.

## Dynamic overlays and readability
Draw routes with dark underlay and gold line at constant CSS width. A point tagged transport:'ferry' represents a distinct ferry connection: use a differentiated dashed line, never a land surface. Reduced-motion frames must be deterministic. Draw an avatar/bike around14–18 CSS pixels, independent of physical collision radius. Parked bike and cart use passed coordinates. Actor stays above surfaces/routes, and labels must not obscure it. Garden entry, if provided, is a fictional game venue; do not invent a greenhouse footprint.
Use screen-space text at least11 CSS pixels, preserving full names. Street labels: at most the selected destination and nearest within60 metres. Overview: at most selected and nearest to avatar. Keep every destination marker; the game's separate DOM list provides crowded-marker access. Place selected labels above/below/beside the anchor, clamp to viewport and reserve avatar clearance. Never shrink below11 or truncate. Skip nonselected labels if they cannot fit; selected long names may wrap. Return accurate full-text label rectangles. Include readable source credit "地理轮廓：Kadaster / PDOK BGT · CC0" and a meaningful scale bar without dominating play.
