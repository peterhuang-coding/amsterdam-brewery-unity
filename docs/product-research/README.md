## R01

**城市下潜：找到可以反复玩的统一探索操作** · [Notion 任务](https://app.notion.com/p/3db3285284df81e683bac3a0cb9140d5?pvs=204)

**2026-09-18 阶段进展：** 用户试玩反馈「挺好玩」，随后「你就做吧」批准超市内部、夜店音乐/人群、自行车过桥及白天线索/次日后果。已交付 [c7b4a27](https://github.com/peterhuang-coding/amsterdam-brewery-unity/commit/c7b4a27)；[规格](https://github.com/peterhuang-coding/amsterdam-brewery-unity/blob/codex/location-depth/docs/superpowers/specs/2026-09-18-location-depth-design.md) · [验收证据](../../.claude/autopilot/rounds/2026-09-18-location-depth.md)。63 条目测试、独立审查与浏览器闭环通过，保持待验收。其他地点深度、工具成长和人物链未自动批准。

**2026-09-16 历史阶段进展：** 用户在夜探 2 提案后回复“开干”，先实施街况与环境互动。已交付三夜局势、3瓶引诱、拖桶阻挡及自动取箱策略；[玩法提交 d10778f](https://github.com/peterhuang-coding/amsterdam-brewery-unity/commit/d10778f) · [规格](https://github.com/peterhuang-coding/amsterdam-brewery-unity/blob/codex/night-exploration-2/docs/superpowers/specs/2026-09-16-night-exploration-2.md) · [验证记录](../../.claude/autopilot/rounds/2026-09-16-night2.md)。下列是原始研究清单；本轮采用已批准切片验收，不声称完成A/B/C玩家比较。Notion当前待验收，下一步等试玩判断。

**要回答的问题：** 玩家在街头探险时反复做什么，为什么第二次还想出门？

**待验证假设：** 观察机会→使用工具/交涉改变局面→携带战利品→决定继续或撤退，可以成为跨街区复用的核心，而不是每个店一个独立小游戏。

**候选路径：** A 自由移动与实时工具；B 自动移动、关键处手动决策；C 路线卡选择。优先比较 A/B 的控制感，C 作为低成本对照，尚未选定。

**最小实验候选：** 只用一个街区、三种机会、三种可复用行动、一项可丢失的携带物与两个撤退口。相同规则换三个 Seed，设计十分钟连续探索；不先扩大量地点。

**阶段边界：** 批准「仅调研」只交付证据、对比和实验设计；最小原型需另行批准。需要玩家的验证在真实试玩后记录。

**验收标准：** 输出一张操作循环图、A/B/C 对比、三局可复盘的分歧案例、一个推荐实验及反例；人工试玩观察是否主动改道和能否提出第二局策略，未试玩不写成通过。

**否定条件：** 如果变化只来自事件文案，或玩家始终机械点击收益最高按钮，说明核心操作仍未成立。

**白天决策点：** 先比较自由操控还是自动行进？先批准调研即可，选定实验后再批准原型。

**执行基线与依赖：** 调研文档：codex/product-research-nightshift；探索代码参考本地 fe36319；实现基线待白天确定

**代码/设计入口：** [tools/prototype/index.html](../../tools/prototype/index.html)；[tools/prototype/core-loop.js](../../tools/prototype/core-loop.js)。

**当前证据状态：** 候选假设，尚未执行本项研究；不能把本页写成已验证结论。

## R02

**候选路径：** A 固定作息加随机事件；B 热度与阵营驱动全城模拟；C 章节化脚本。先调研 A 的小规模因果，B 的成本作为反例。

**最小实验候选：** 一个街区、四个时间点、三个有作息的人物、两条跨日后果：白天看到线索、夜里出现机会、次日有人回应。黑色幽默来自旅游包装与城市生活的落差。

**验收标准：** 输出时间/地点/人物表、三条跨日因果、一次错过与一次补救路径；能区分规律变化与随机变化；先写观察方案，不把模拟运行当真实玩家反馈。

**否定条件：** 如果玩家无法提前推断任何变化，或后果只有好感数字变化，就缩减随机量并补可见反馈。

**白天决策点：** 更看重生活真实感还是夜间危险感？候选题材含夜生活与灰色地带，具体内容尺度由白天决定。

**要回答的问题：** 批次、补救和限时订单怎样推动探索，而不把所有活动都变成加酒或加钱？

**候选路径：** A 探险收益主要进入经营；B 探险与生活各有独立回报、共享时间和人物；C 纯经营主线。A/B 作为候选，C 与既有探索目标的差异必须明确。

**阶段边界：** 批准「仅调研」只交付证据、对比和实验设计；最小原型需另行批准。需要玩家的验证在真实试玩后记录。

**验收标准：** 输出物品来源→携带→入库→批次→出售的流向、三个相互有代价的策略、两版模块衔接表；列存档隔离/迁移方案和现有入口冲突，不默认合并。

**否定条件：** 如果每次最优解都是同一条路线，或不上支线就必死，应重做收益与替代路径。

## R06

**自动播放与手动选择：让观看也有参与感** · [Notion 任务](https://app.notion.com/p/3db3285284df81ecae92f8907e6e970c?pvs=204)

**要回答的问题：** 什么事情适合自动做，什么决定必须停下来让玩家接管？

**待验证假设：** 自动行进省去重复操作，危险、改道、承诺和撤退保留决策，能兼容轻松观看和主动探索。

**候选路径：** A 自动走路、交互手动；B 自动处理低风险事件、重要选择暂停；C 全手动。比较停顿频率、可理解性与操控感。

**最小实验候选：** 同一段十分钟路线展示 A/B/C；包含一次自动暂停、一次手动接管、一次跳过机会、一次刷新恢复和一段长路无事件。

**阶段边界：** 批准「仅调研」只交付证据、对比和实验设计；最小原型需另行批准。需要玩家的验证在真实试玩后记录。

**验收标准：** 输出自动/手动控制边界、状态转移、恢复与防卡住验收用例；记录每个暂停的原因；主观烦躁感交给玩家，不用按钮可点替代趣味验证。

**否定条件：** 如果频繁弹窗打断观察，或自动模式替玩家承担不可逆后果，缩减自动范围。

**白天决策点：** 默认自动到什么程度？现有用户偏好是自动行进、关键处选择、随时手动，具体边界待调研。

**执行基线与依赖：** 主要参考本地 fe36319 自动选择与播放控制

## 每项研究的统一交付

1. 一页结论：推荐什么，支持它的证据是什么，什么结果会推翻推荐。
2. 备选方案：至少一个值得比较的方案及取舍。
3. 最小实验：范围、基线、验收和停止条件；未批准前不做生产实现。
4. 证据分层：代码实际行为、官方/一手外部来源及访问日期、真实玩家反馈、仍待验证的假设。
5. Git 提交、Notion 结果回链，以及恰好一个下一次白天的决策问题。

涉及可变软件、引擎版本、许可、竞品现状时，执行调研时再查官方或一手资料。没有实测、不足样本、访问失败必须如实记录。当前没有新竞品或引擎实测结论。
