# 从规则原型到可信的城市游戏：玩法与引擎选择

日期：2026-09-12。性质：设计与技术选型建议；未迁移引擎、未恢复旧 Unity 工程、未改变游戏规则。继承前一份城市/社交设计，补充“更真实、更好玩”的优先级。默认按桌面单机目标讨论；最终发行平台仍由用户偏好决定。

后续反馈与原型收敛见[探索式玩法重审](2026-09-12-exploration-prototype-redesign.md)：用户仍认为打捞、啤酒过于简单，下一原型建议改为可用工具与线索解决同一问题的《被淹的仓库》，保留本稿的街区/酒馆与长期经营目标。

## 结论与适用条件

如果目标是有完整街区、角色操作、持续故事、以后面向 Steam 的单机游戏，推荐让 Unity 承担下一份正式场景切片，现有 Web 原型保留为规则基线。先用一个小街区证明操作、美术制作和构建工作流，再迁移后续区域。

如果最重要的是手机浏览器点击即玩，则优先选择 Web 游戏框架，并围绕触屏、短局和加载预算设计。Phaser 的官方定位就是面向桌面和移动浏览器的 2D 框架，支持 JavaScript/TypeScript、WebGL/Canvas；它没有内置 3D 渲染和物理。这条路线也能做分层的 2.5D 视觉。[Phaser 官方定位](https://docs.phaser.io/phaser/getting-started/what-is-phaser)

引擎与发行平台是两个选择：Unity 同样能够发布到 Web。浏览器版本需要单独验收加载、输入、音频、内存和运行表现，不能把桌面构建成功当作浏览器也达标。[Unity Web 支持](https://docs.unity3d.com/6000.3/Documentation/Manual/webgl.html)；[Unity Web 限制](https://docs.unity3d.com/6000.3/Documentation/Manual/webgl-technical-overview.html)

## 2. “真实”优先做三件事

### 世界有自己的秩序

先给三个主要人物安排可理解的日程：Bram 白天在咖啡馆，Lotte 准备演出，Marta 在街坊之间走动。天气和时段改变他们的位置与行为，玩家有办法提前获知去向。无需模拟全城几百个人。

街区闲逛和读对话低压力；确认有收益的活动时清楚显示占用哪个时段。活动内部可以有短倒计时。用同一套日程驱动商店营业、人物出现、任务截止和生产完成，避免互相矛盾的时间提示。

### 事情有来源，也会留下痕迹

目前“按一次获得工资”“捞到瓶子直接增加可售酒”是验证经济的简化动作。正式体验里，工作有可完成的短任务；打捞可以得到押金瓶、工具或原料，不让所有东西凭空变成酒。货物进仓库、酒桶接到酒头、菜单与库存一致。

生产加入游戏内跨日完成的批次，玩家可以预留明晚的酒。提供起始库存、可购买成品和明确的完成时间，避免新玩家开局只能等待。时间压缩服务于玩法，不要求现实小时级等待。

演出之后留下海报、借过的设备出现在店里、帮助修好的门不再破损。少量持续变化让玩家认得自己的选择。

### 操作能感到重量

走路的起停、端酒时的姿态、碰杯声、推门后雨声变闷、酒液和泡沫的反馈，都比继续增加面板更直接地改善在场感。需要一套一致的尺寸、镜头、动画和音效规范。

只保留能产生选择或熟练感的摩擦：搬多了走得慢，可以少带或借车；杯子不足影响一段高峰，可以提前准备。重复洗杯、收垃圾等事务应允许批量处理、设备升级或雇人接手，不用饥饿、如厕等额外数值填满游戏。

## 3. “好玩”需要一个真正能练习的白天玩法

夜间已有库存与队列雏形，白天的三航道打捞还不足以支持长期反复玩。优先把一次出门做深：选择安全或冒险路线、观察环境、装载有限货物、决定何时回家。

最适合先验证的是现有运河打捞的运输版本：可操作的小船、固定街区里的几条短水路、不同体积的货物、会预告的障碍和返航选择。打捞物能用于晚间营业或人物委托。失败失去本次部分收获，玩家清楚下一次怎样改进。

货运自行车是有城市特色的后续候选，可以带来装载、转弯、捷径和送货顺序等操作；只有运河运输先证明有趣后再考虑第二套载具。先不同时展开赛车、钓鱼、潜行等多个大系统。

夜间的深度则来自提前准备和空间安排：酒头、储酒和座位位置会影响服务路线；客人需求和熟人承诺影响先后；升级让同样的忙碌产生新解法。先把服务动作的响应做顺，再增加工作站。

成长应该让玩家从亲自端每杯酒，逐渐能交给帮手处理基础订单，自己处理特殊客人、调酒款与演出。不能只是每个阶段再增加一个同时倒计时的劳动。

## 4. 社交和肉鸽需要重新划分持久边界

这是对上一份讨论稿的进一步修订建议，尚未替换当前存档规则。

三天后全量重开适合快速试验，但长期人物关系与每轮清空存在冲突。正式方向更适合“持续的酒馆生活 + 短周期经营挑战”：

- 城市布局、人物已经发生的故事、店铺外观和已解锁的配方持续保留。
- 每个经营周期改变订单、供应、事件组合和临时设备选择，产生经营方式的差异。
- 挑战失败可以失去本期奖金、部分周转资源或承担一笔可处理的债务；人物按发生的事实回应，并允许补救。
- 实验用挑战模式仍可提供同 seed 重试和完全新开档。剧情进度与挑战记录分开，不把人物“忘记你”当作无解释的默认行为。

若用户最终更偏爱纯肉鸽，可采用局外人物故事持续、局内临时承诺重置的方式；这需要清楚的叙事解释。当前更推荐持续经营，是否提高到七天周期在短片段试玩后决定。

关系用经历和互惠表现：Bram 愿意借设备，Lotte 能带来演出，Marta 会告诉你街坊的需求。帮助他们各自带来新机会与新约束，不能让所有朋友都只是同一种收入加成。

黑色幽默要给玩家周旋的余地。例：房东因演出投诉噪声，又要求按演出用途加租，并预留第一排。玩家能换不插电演出、借场地或接受额外成本；账单和现场行为承接笑点。角色也应有温暖、普通和沉默的时刻，避免所有人每句话都像讽刺段子。

## 5. 引擎与美术的取舍

以下为本项目的判断，属于基于目标与现状的推论，不是对引擎的通用排名。

| 路线 | 适合承担什么 | 本项目需要付出的主要成本 | 建议 |
|---|---|---|---|
| 现有 Canvas/DOM 原型 | 数值、事件因果、低成本规则试验 | 场景编辑、动画、遮挡和资源工作流要继续自建 | 保留作稳定规则参照 |
| Web + Phaser | 以浏览器即玩为核心的 2D 游戏 | 重做当前场景与交互层；美术和内容仍需制作 | 浏览器优先时推荐 |
| Unity | 正式桌面单机、可编辑的街区和角色操作 | 重建有效工程、迁移规则、打通真实编辑器与构建验收 | 桌面优先时推荐 |
| Godot | 以 2D 为主、希望采用开源工具的制作路线 | 同样要迁移当前 JS，并建立新的制作和验收流程 | 可行替代，当前没有证据证明再转一次更省成本 |

Godot 官方提供独立的 2D 编辑、物理、TileMap、动画与光照工作流；它具备承载此类视觉的能力，不能因为仓库名字含 Unity 就排除。[Godot 2D 官方说明](https://docs.godotengine.org/en/stable/tutorials/2d/introduction_to_2d.html)

推荐的首版画面是固定斜视角、分层街景、风格化人物和明显的前后遮挡。先用 2D 素材与光照完成一间酒馆和街角，以可编辑性和美术一致性决定是否加入低模 3D 建筑；不先做可自由旋转的大型 3D 城市。Unity 的 URP 提供 2D 光照与阴影；混合 3D 物件也有官方路径，但需要匹配着色器和排序，不能当作自动兼容。[2D 光照](https://docs.unity3d.com/6000.3/Documentation/Manual/urp/2d-index.html)；[混合 3D 物件](https://docs.unity3d.com/6000.3/Documentation/Manual/urp/2d-renderer-urp-features-landing.html)

版本方面，截至本轮查证，6.3 LTS 受支持到 2027 年 12 月，6.6 是当前更新版本，6.5 已结束该更新周期的支持。新制作工程可评估 6.3 LTS；恢复历史 6.5 工程则应隔离验证兼容性，不能直接用更旧编辑器原地降级打开。[Unity 支持政策](https://unity.com/releases/unity-6/support)；[6.6 发布](https://discussions.unity.com/t/unity-6-6-is-now-available/1735357)；[6.5 支持说明](https://discussions.unity.com/t/unity-6-5-is-now-available/1723176)

## 6. 下一份交付必须同时证明玩法与制作流程

保留上一轮的 Jordaan 小街区目标，将其作为 Unity 试制的候选内容，不再继续大规模扩展 Web 街景。这个建议取决于桌面优先的产品目标，尚未开始迁移。

目标体验为约 15 分钟的“一个下午 → 开店 → 次日反馈”：一条街、一家酒馆、三个熟客、一趟有装载取舍的短打捞、一条两种解法的人物事件。镜头、脚步、雨声、开门、端酒反馈也必须在这个片段里体现。该时长是制作目标，不是已有实测数据。

迁移时继承规则与测试案例，按场景选择重做输入与显示。当前 JS 不能直接作为 C# 运行；旧 Unity 程序也没有实现当前三天规则。用固定输入/事件表/期望账本核对资金、库存、承诺和日期变化，避免默认认为不同语言的随机数生成会产生相同 seed 序列。只维护一份新规则的权威实现，Web 基线保留稳定样例，避免长期双写两套完整游戏。

验收顺序：

1. 编辑器真实 Play Mode 能走动、进门、互动；构建后的独立桌面程序也通过。单看 C# 文件或静态检查不算完成。
2. 转场、遮挡、碰撞、暂停、存档、读档和高峰期操作可用；在选定目标设备上实际测量帧率与输入体验。
3. 试玩者能无需解释找到第一件事，愿意练习打捞，能指出白天选择如何影响晚上，并且有下一次想尝试的不同做法。
4. 若纯走路/端酒仍觉得烦，优先缩短空走、改善输入和删减机械劳动；若玩法没有差异，先改选择与后果；不要用更多街区和更贵美术掩盖问题。

制作的真正长期成本会在街景资产、角色动画、声音、任务内容和反复试玩。换引擎可以改善制作工具与呈现能力，趣味仍要靠这个小片段的结果决定后续投入。
